# AArch32 decoder

`uml_arm64_aarch32_decoder` is the one decoder for the 32-bit Arm line. Both
arm64 engines and the AArch32 semantic library share it. It decodes A32,
T16 and T32 words, in the IT state the caller holds, and answers with the
instruction's form, condition, length, operands and IT effect. It includes no
engine, holds no state, and is a CPU-layer `shared` target.

## Contract

`decode.hpp` is the decoder's interface and `semantics.hpp` the semantic
library's; their comments state what each call takes, returns and guarantees,
including the fault ordering and what each exit leaves in the PC and
ITSTATE, which the engines follow. `a32_profile.hpp` builds the `Profile` an
engine decodes against from the host.

The profile is Armv8-A AArch32 at EL0 (see
[`../../../../docs/architecture.md`](../../../../docs/architecture.md) and
[`../../../../docs/a32-instruction-coverage.md`](../../../../docs/a32-instruction-coverage.md)).
The decoder implements these choices on top of the XML:

- SWP and SWPB, which Armv8 AArch32 does not have, decode as unallocated;
  SETEND, SETPAN, SRS, RFE, ERET, HVC, SMC, HLT, DCPS, the banked-register and
  user-register forms of MRS, MSR, LDM and STM, and LDC and STC are undefined
  at EL0;
- MRS and MSR reach the APSR only, and VMRS and VMSR reach FPSCR only
  (including `VMRS APSR_nzcv, FPSCR`); an MSR whose x field (mask bit 1) is
  set would write PSTATE.E, which the profile does not implement (SETEND is
  undefined), so it is undefined, and its c field is ignored at EL0;
- CPS is a NOP at EL0 and BXJ behaves as BX;
- an A32 data-processing instruction with S set and Rd 15 (an exception
  return) is UNPREDICTABLE at EL0, hence undefined;
- an encoding the XML marks should-be-zero or should-be-one that differs is
  UNPREDICTABLE, hence undefined;
- the hint encodings of features the profile lacks (ESB, TSB, CLRBHB) are
  NOPs, as are the reserved hint encodings whose should-be bits (SBO in an A32
  hint's bits 15:12; in a T32 hint, SBO in the first halfword's low nibble
  and SBZ in bit 13 and bits 11:8 of the second) hold; one that differs is
  UNPREDICTABLE, hence undefined.

## The table

`a32_encodings.hpp`, `a32_encodings.cpp` and `a32_operand_decode.cpp` are
generated by `tests/tooling/arm64/generate_a32_encoding_table.py` from the
pinned Arm AArch32 XML release, the profile's choices
(`tests/tooling/arm64/a32_profile_policy.py`) and LLVM MC 22.1.8, a
tooling-time oracle that no build uses. Never edit them.

- Form names are the XML's, with one correction: Arm's 2026-06 XML names the
  A32 VRSRA encodings against their own Q field, so the catalog swaps them
  (`XML_NAME_ERRATA` in `a32_architecture_oracle.py`, which fails the
  generation once the XML is corrected).
- A `Form` is one XML encoding. A `Row` is one partition of the A32 or T32
  encoding space that the XML's encoding index allocates to a form; the index
  partitions the space exactly, so the rows that remain after the unallocated
  ones are dropped decide every word. A decision tree per instruction set
  selects the candidate rows, which the row's mask, value and constraints then
  confirm.
- An operand program is a form's Decode pseudocode translated to C++ by
  `a32_operand_codegen.py`. The helpers it calls are Arm's shared
  pseudocode functions in `decode_support.hpp`. A construct the translator
  does not know fails the generation.
- `form_operation.hpp` groups the forms into operations (`Op`) by mnemonic,
  with each form's operand shape and SP base read from its name. It is the
  one such table: the semantic library adds its handlers and transfer modes
  to it, and the JIT's compiler adds its classes for the VFP, Advanced SIMD
  and Armv8 forms.
- The unit test `arm64-aarch32-decoder` decodes the stored sample words of
  every row and the whole 16-bit Thumb space and compares the answers
  against `a32_expected.py`, an independent evaluation of the same pseudocode
  and rules, and against what LLVM MC decodes
  (`tests/unit/arm64/aarch32_decoder/`). `docs/testing.md` has the commands.

## The semantic library

`uml_arm64_aarch32_semantics` is the one C++ implementation of what the
decoder accepts, for the engines' slow paths and long tails and for the
corpus's model lane (`semantics.hpp`). It is a CPU-layer `shared` target that
includes no engine, works on `CpuState` alone and reaches guest memory only
through the caller's `A32Memory`.

The engines reach it through `execute_a32`, with the instruction they
decoded; `step_a32`, which fetches and decodes as well, is the model lane's
and the semantic tests' entry. It covers the whole profile, A32 and T32
([`../../../../docs/a32-instruction-coverage.md`](../../../../docs/a32-instruction-coverage.md)
lists the forms). The unit tests that require a lowered form to stay out of
the library link `uml_arm64_aarch32_semantics_exit_counting`, the library
built with per-form counters of `execute_a32` calls
(`semantics_exit_counters.hpp`); the library the products link has none.

Floating point runs the host's own scalar instruction on bit patterns under
the FPCR the form defines, the guest's control bits for VFP and the Standard
FPSCR value for Advanced SIMD, and merges the cumulative flags it raised into
`fpsr`. FPSCR is split across `CpuState` as the engines hold it: the control
bits in `fpcr`, the cumulative flags and QC in `fpsr`, and N, Z, C and V in
`a32_fpscr_nzcv`; Len, Stride and the trap enables read as zero and ignore
writes. VRECPS and VRSQRTS are AArch32's unfused steps, not the A64 fused
ones, and the fixed-point VCVT to floating point rounds to nearest even as
its pseudocode says. A half-precision result zero-extends into its S
register, and the arithmetic ignores FPSCR.AHP, which only the conversions
read. The Advanced SIMD conversions from half precision to 16-bit integers
use the host's H-register forms, whose saturation raises Invalid Operation
for that lane alone, because the lanes of one instruction share the flags.

The profile presents BFloat16, the 8-bit matrix multiply and FHM only where
the host has them, but the library implements all three without them, so the
corpus model lane tests every form on any host: the BFloat16 dot product,
matrix multiply and conversions are the architecture's round-to-odd
arithmetic in integers, the 8-bit forms are integer, and VFMAL unpacks its
half-precision operands as the A64 FMLAL helper does (FZ16 flushes a
denormal, AHP is ignored) into the host's fused single-precision
multiply-add. VJCVT is integer arithmetic too, because the architecture
clears Z for a negative zero and for a subnormal that FPSCR.FZ flushes,
which the host's FJCVTZS does not do on every core. AES and SHA run as the
host's own instructions on copies of the registers, and an iOS build compiles
the library with the inline-assembly architecture option the other CPU
implementation targets use.
